# AZAS-APP · Expo 해커톤 하네스

React Native + Expo 프론트엔드 데모를 위한 프로젝트 초기 구성이다. 앱 아이디어·주요 화면·시연 플랫폼을 정한 뒤 화면 개발을 시작한다.

프로젝트 구성일: 2026-11-14. 외부 스킬 선택·검사 시점은 `skill-sources.json`의 원본 기록을 따른다.

프로젝트 스킬 15개는 `.agents/skills/`, Codex 기본 설정과 에이전트 3개는 `.codex/`에 포함되어 있다. 외부 스킬 14개는 원본·검사·승인 기록에 고정된 파일을 사용한다.

## 시작

이 프로젝트에서 새 Codex 세션을 열고 “이 앱은 …이고, 먼저 … 화면 만들어줘”라고 요청한다. 프로젝트를 신뢰해야 `.codex/config.toml`을 읽는다. 새 세션에서 모델/effort가 `gpt-6.1-sol / low`인지 확인한다. UI에서 지정한 값이나 상위 정책이 우선할 수 있다. 현재 대화의 모델은 파일 생성만으로 바뀌지 않는다.

일상 구현은 메인이 처리한다. 첫 핵심 화면·큰 리디자인은 `expo-ui`(Sol medium), 명세가 확정된 독립 작업은 `expo-quick`(Luna low), 원인 추적에 막힌 오류는 `expo-debug`(Sol high)에만 맡길 수 있다. 보조 동시 1개, 재위임 없음. 이 배정은 비용/품질에 대한 설계 판단이며 절감 효과는 사용 후 측정한다.

연결 스킬과 설치 상태는 [스킬 목록](skill-inventory.md), 고정 커밋과 보안 판정은 [원본 기록](skill-sources.json)에 있다. 실행 때에는 `.agents/skills/expo-hackathon/references/skills.md`의 해당 작업/담당 절만 읽는다. 코딩 원칙은 Ponytail, 첫 시각 방향은 UI UX Pro Max, 실제 앱 구현은 Expo 공식 스킬, 관련 React Native 지침은 Vercel 스킬이 맡는다. 설치 보류된 항목은 부르지 않는다.

Context7은 프로젝트 전용 원격 MCP로 `resolve-library-id`, `query-docs` 두 도구만 연결한다. 초기화와 도구 목록 조회를 확인했으며, 실제 문서 조회에는 서비스 한도/인증이 적용될 수 있다. 공개 라이브러리명·버전·오류 요약만 질의하고, 코드 전문·대화·비밀값은 보내지 않는다. 연결 설정을 점검한 것이며 원격 운영 서버의 구현 전체를 감사한 것은 아니다. 기존 Headroom MCP를 재사용하고 새 프록시·훅은 설치하지 않는다.

코드·디자인 리뷰는 “리뷰해줘”라고 요청할 때만 한다. 실행·타입 오류 확인은 구현의 일부로 남긴다. 장기 유지보수·대형 아키텍처·CI·테스트 확대는 이번 데모의 기본 범위에 넣지 않았다.

## 저비용 기록

작업 시작과 끝에 에이전트가 `scripts/hackathon/bench.py`를 실행한다. 사용자에게 매번 입력을 요구하지 않는다. 별도 모델 호출·백그라운드 프로세스·네트워크·설치 의존성이 없으며 Python 표준 라이브러리만 사용한다. 셸 호출과 결과를 읽는 문맥 비용까지 0인 것은 아니다.

```sh
python3 scripts/hackathon/bench.py start home-01 '홈 화면 및 상세 이동'
python3 scripts/hackathon/bench.py end home-01 --check passed --rework 0
# 사용자가 결과를 실제로 확인한 경우에만:
python3 scripts/hackathon/bench.py accept home-01
# 하루 끝이나 발표 준비 때:
python3 scripts/hackathon/bench.py report
```

`_workspace/metrics/tasks.json`에 작업별 시작/종료·경과시간·검사 결과·재작업·사용자 확인 여부·모델/effort·세션별 관측 토큰을 남긴다. 보고서는 같은 폴더의 `report.md`. 기록은 기본 git 제외이므로 공모전 제출 전에 필요한 요약을 따로 보관한다. `probe`는 현재 세션 카운터를 읽을 수 있는지 확인하며 장부에 작업을 추가하지 않는다.

기록 권한은 프로젝트의 토큰 수치 수집에 한정한다. `CODEX_THREAD_ID`/`CODEX_SESSION_ID`로 선택한 이 프로젝트의 세션과 그 자식 세션만 집계한다. 다른 프로젝트 대화는 집계하지 않는다. 수집기는 세션 메타데이터와 사용량 필드만 보존하고 메시지 본문·코드·도구 인자는 출력·저장·외부 전송하지 않는다. 원본 로그는 읽기 전용이다. 전역 HarnessKit 코드는 바꾸지 않았다.

## 토큰을 어떻게 재는가

기존 HarnessKit의 `hktokens.py --runtime codex`는 Codex 로그를 집계하지 않고 시간만 기록한다. 이 프로젝트에서는 사용자 요청인 실제 정량 기록을 위해 로컬 `~/.codex/sessions/`의 `event_msg → token_count → info.total_token_usage` 연결을 추가했다. 이 경로는 현재 설치본에서 확인한 내부 형식으로, 공식적인 호환성 보장이 아니다. 형식 변경/누락/접근 실패는 미측정으로 처리한다.

- 시작·종료에 각 세션의 **최신 누계 하나씩만** 가져와 차이를 계산한다. 이벤트의 누계들을 전부 더하지 않는다.
- 입력·캐시 입력·출력·추론 출력·총계는 따로 보존한다. 캐시는 입력, 추론은 출력에 포함되므로 총계에 다시 더하지 않는다.
- 실제 개발 서브에이전트와 권한 심사 시스템(guardian)의 사용량을 분리한다. 이 시스템 심사는 사용자가 요청할 때만 하는 코드 리뷰와 다른 기능이다.
- 누계 초기화·필드 누락·대상 세션 불명은 0으로 숨기지 않는다. 일부만 측정되면 전체 토큰은 미측정이다.
- 로그 반영이 늦으므로 마크가 관측한 시각까지의 수치다. 마지막 보고 응답은 아직 안 적혀 빠질 수 있고 시작 직전 응답이 들어올 수도 있다. **작업 전체의 정확한 청구 토큰/요금/계정 한도 사용량으로 쓰지 않는다.**
- 경과시간에는 사용자 대기·휴식·빌드도 포함된다. 순수 작업 시간·모델 추론 시간으로 바꾸어 부르지 않는다. 재작업은 에이전트가 실제 수정 근거로 표시한 횟수이며 자동 버그 탐지 수치가 아니다.

## 공모전용 비교

일반 개발 기록만 있어도 “완료 기능 N건, 경과시간, 관측 토큰, 재작업 횟수, 사용자 확인”을 제시할 수 있다. “몇 % 아꼈다”는 말에는 비교군이 필요하다. 해커톤 도중 같은 앱을 억지로 두 번 만들지 않는다. 원하면 종료 후 작은 동일 과제를 별도 임시 폴더에서 1~3쌍 비교한다.

```sh
# 실제로 하네스 없이 수행할 별도 기준선 작업에서:
python3 /path/to/AZAS-APP/scripts/hackathon/bench.py --project /path/to/baseline start baseline-01 '목록+상세' --variant baseline --pair list-01 --spec '목록 10개, 상세 이동, 뒤로가기; 동일 시작 코드 v1'
# 완료 후 end, 사용자 확인 후 accept
# 같은 완료 조건의 하네스 적용 작업에서:
python3 scripts/hackathon/bench.py start harness-01 '목록+상세' --variant harness --pair list-01 --spec '목록 10개, 상세 이동, 뒤로가기; 동일 시작 코드 v1'
```

기준선 폴더에서는 이 하네스의 지침을 적용하지 않는다. 이 스크립트를 같은 측정 조건으로 사용하고, 그 폴더의 CODEX_THREAD_ID로 측정한다. 기준선의 start/end/probe에는 모두 `--project /path/to/baseline`을 붙인다. 결과는 수집 스크립트가 있는 폴더의 장부에 모인다. `--pair`와 `--spec`는 식별 표식이며 실험 조건을 자동으로 검증하지 않는다. 사람이 시작 코드·완료 기준·기기·네트워크·관측 범위·UI 품질이 비교 가능한지 확인한 뒤 accept한다. 설정 모델만 기록하지 말고 `tasks.json`의 실제 관측 모델/effort도 함께 공개한다. 모델 목록은 해당 세션에서 관측한 값이며 작업별 토큰의 모델별 배분은 아니다.

감소율 = `(baseline - harness) / baseline × 100`. 동일 spec, 동일 pair의 완료·사용자 확인된 작업 한 쌍이 있을 때만 계산한다. 음수도 그대로 남긴다. 모델/effort가 다르면 “킷을 포함한 운영 구성 전체의 차이”이며 “킷 지시문만의 효과”로 발표하지 않는다. 한두 쌍의 결과는 사례 측정이다. 순서·학습 효과와 관측 누락을 적는다. 작업별 UI 평가는 원할 때 사용자에게만 받으며 에이전트가 높은 점수를 만들어 넣지 않는다.

하네스 제작·계측기 작성·A/B 반복 비용은 별도로 공개한다. 개발 작업 통계에 섞지 않으려면 `--variant setup`으로 기록한다. 이번 구성 작업은 계측기가 완성되기 전 시작했으므로 전체 제작 비용은 측정하지 못했다. 테스트 픽스처와 probe 결과는 성과 수치로 넣지 않는다.

하네스 구성은 HarnessKit, 생성 스킬 형식 검증은 skill-creator를 사용했다. 기본 킷의 자동 리뷰·상시 회고·매 작업 새 세션 규칙은 사용자의 해커톤 운영 조건에 맞춰 적용하지 않았다.
