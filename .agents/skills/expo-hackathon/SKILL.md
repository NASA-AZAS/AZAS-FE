# Expo 해커톤 개발

하루 동안 쓰는 데모 앱이다. 예쁜 화면, 동작하는 핵심 흐름, 적은 토큰 순으로 판단한다. 웹사이트 제작 스킬(Sites)은 이 네이티브 앱 작업에 쓰지 않는다.

## 실행

1. 요청과 관련 파일만 본다. 첫 착수 때만 package.json·라우트·설치된 의존성을 확인한다. 앱이 없으면 아이디어/핵심 흐름/시연 플랫폼 중 필요한 것만 묻고, 확정 후 Expo + TypeScript + Expo Router로 시작한다. 하네스 파일이 있으므로 임시 디렉터리에 scaffold 후 앱 파일만 옮겨 기존 파일을 보존한다.
2. 작업의 끝을 한 문장으로 정한다. API가 없으면 현실적인 로컬 목업으로 먼저 완성한다. 응답 타입과 mock/live 전환은 작은 파일 하나로 격리한다. 서버·인증 인프라·스토어 배포는 요청된 경우에만 다룬다.
3. 메인이 구현한다. [스킬 배정](references/skills.md)에서 이번 작업과 담당에 해당하는 설치된 스킬만 읽는다. 화면 작업은 [UI 운영 조건](references/ui.md)을 함께 따른다. 첫 화면의 테마를 재사용하며 작은 수정에 설계 문서를 쓰지 않는다.
4. 변경에 맞는 최소 실행/타입 확인을 한 번 한다. 데모 흐름을 실행해 볼 수 있으면 확인한다. 전체 리뷰, 전수 감사, 회귀 테스트 확대, 스냅샷 테스트는 사용자가 요청할 때만 한다. 화면을 직접 못 봤으면 시각 확인은 미실시라고 알린다.
5. 바뀐 동작·확인 결과·남은 막힘만 짧게 보고한다. 작업 기록은 아래 스크립트에 숫자로 남기고 매번 회고문을 만들지 않는다.

## 연결 스킬

[스킬 배정표](references/skills.md)가 호출 범위를 정한다. 코딩 원칙은 Ponytail, 시각 방향은 UI UX Pro Max, 실제 Expo 구현은 공식 Expo 스킬, 관련 RN 규칙은 Vercel이 맡는다. 자체 스킬에 이 지침을 다시 작성하지 않는다. 보류·미설치 항목은 호출하지 않는다. 최신 설치 상태: `docs/skill-inventory.md`.

## 모델과 위임

기본 메인 `gpt-6.1-sol / low`. 같은 모델이라도 effort는 토큰·시간에 영향을 준다. 세션 설정은 지침만으로 바뀌지 않으며 `.codex/config.toml`은 신뢰된 프로젝트의 새 세션 기본값이다.

| 에이전트 | 모델 / effort | 호출 조건 | 도구 호출 권고 상한 |
|---|---|---|---|
| expo-ui | gpt-6.1-sol / medium | 첫 핵심 UI·큰 디자인 변경 | 18 |
| expo-quick | gpt-6-luna / low | 명세가 확정된 독립 작업 | 10 |
| expo-debug | gpt-6.1-sol / high | 실제 오류의 원인 추적에 막힘 | 20 |

- 이 스킬은 **위 조건일 때만** 해당 역할에 위임하도록 요청한다. 기본은 서브에이전트 0개, 동시 최대 1개, 위임 깊이 1단계다. 자동 리뷰어는 만들거나 부르지 않는다.
- 작아서 인계 비용이 더 큰 작업은 메인이 한다. 메인이 같은 결과를 다시 만들거나 서브에이전트 변경을 상시 재리뷰하지 않는다. 필요한 통합·실행 확인만 한다.
- 에이전트 입력은 목표·완료 조건·허용 파일·공용 타입/테마 경로·관련 로그만 준다. 전체 대화를 넘기지 않는다. 역할별 TOML을 사용한다. 도구에 사용자 정의 유형 선택이 없으면 해당 TOML을 읽고 명시된 모델/effort로 `fork_turns="none"`을 사용해 위임한다. 설정할 수 없으면 상위 모델로 몰래 대체하지 말고 메인이 진행하며 알린다.
- 에이전트 출력은 5줄 이내. 호출 상한은 지시 수준이며 런타임의 강제 토큰 한도가 아니다. 상한에 닿으면 완료·남은 일만 반환한다.
- 모델·effort의 비용 효과는 측정 전에는 예상이다. 사용자가 선택한 모델을 임의로 바꾸거나 API로 별도 과금되는 실행을 추가하지 않는다.

## 기록과 토큰 절약

- 메인만 작업당 시작/종료 두 번 기록한다. 첫 구현뿐 아니라 사용자 피드백을 반영한 수정도 기록한다. 단순 질문은 기록하지 않는다. 기록 명령은 가능하면 기존 작업의 셸 호출에 함께 넣고 출력 한 줄만 읽는다. 계측을 위한 별도 LLM·상시 훅·외부 전송은 없다. Context7 문서 질의의 외부 전송과는 별개다.
- 시작: `python3 scripts/hackathon/bench.py start <고유-id> '<작업>'`. 끝: `python3 scripts/hackathon/bench.py end <고유-id> --check passed` (`failed`/`not-run`도 그대로 남김). 막히거나 취소되면 `--status blocked`/`cancelled`. 기능의 버그·요청 미충족을 고친 횟수만 `--rework N`으로 적고, 새 요구사항은 재작업으로 세지 않는다.
- 사용자가 결과를 확인했을 때만 `python3 scripts/hackathon/bench.py accept <id>`. 에이전트의 완료 판정과 사람의 확인은 구분한다. 확인을 요구하며 작업을 중단하지 않는다.
- 기본 킷 `hktokens.py`의 Codex 경로는 시간만 지원하므로, 이 프로젝트는 `bench.py`가 로컬 Codex 카운터의 차이를 기록한다. 본문·코드·도구 인자는 내보내지 않는다. native 로그 형식이 바뀌거나 접근할 수 없으면 실패를 짧게 남기고 앱 개발을 계속한다. 수치를 추정으로 채우지 않는다.
- 관측 마크 경계에는 로그 반영 지연이 있다. 결과는 **관측 토큰**이며 마지막 보고 응답 일부가 빠질 수 있다. 캐시·추론 토큰을 총계에 중복 합산하지 않는다. 권한 심사 시스템 사용량은 별도 열이다.
- 발표나 하루 마감 요청 때만 `python3 scripts/hackathon/bench.py report`로 `_workspace/metrics/report.md`를 만든다. 같은 범위의 기준선이 없으면 절감률을 말하지 않는다. 비교 절차·측정 한계는 [운영 안내](../../../docs/hackathon-harness.md)를 필요할 때만 읽는다.
- 변경 파일 위주로 읽고 로그는 필요한 끝부분만 본다. 이미 통과한 검사를 이유 없이 반복하지 않는다. 하네스 스캔/카탈로그/웹 조사는 하네스를 고치거나 필요한 API를 확인할 때만 한다.
- 기능 하나가 끝났거나 세션을 바꿀 때만 `_workspace/STATE.md`에 결정·관련 경로·실행법·다음 할 일을 40줄 이내로 남긴다. 매턴 갱신하지 않는다. 대화가 길면 이 파일로 인계할 수 있지만 새 세션을 강제하거나 매번 확인받지 않는다.

## 피드백 처리

색·간격·문구·동작 피드백은 해당 부분만 바로 수정한다. 작업 방식·모델 배정·토큰 과다 같은 하네스 피드백은 HarnessKit evolve로 범위만 조정하고 원래 작업을 잇는다. 자동 회고·자동 하네스 개편은 하지 않는다.

## 동작 예

- “홈 화면 만들어줘” → 첫 UI 방향·핵심 동작 구현·최소 실행 확인·관측 기록. 자동 리뷰 없음.
- “버튼 색만 바꿔줘” → 메인이 해당 스타일만 수정. UI 에이전트·전체 탐색 없음.
- “API가 아직 없어” → mock으로 데모 흐름 완성. 서버 구현 없음.
- “리뷰해줘” → 요청한 범위만 메인이 리뷰. 수정은 요청 맥락에 따라 진행.
- 실행 오류/기록 실패 → 앱 오류는 좁혀 해결, 측정 불가는 미측정으로 남기고 앱 작업 계속.
